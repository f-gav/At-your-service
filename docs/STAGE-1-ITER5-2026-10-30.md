## Реальный PostgreSQL, без риска для пользователей

В `.github/workflows/deploy.yml` добавлен независимый job `rpc-quota-postgres`, предоставляющий **временный PostgreSQL 17** посредством GitHub Actions service container. В нём нет ключей Supabase, JWT, файлов пользователей или копий рабочей базы.

Ступени:
1. `tests/fixtures/room-rpc-local-schema.sql`: создать схемы `auth`, `public`, роли `anon` и `authenticated`, тестовые персонажи, комнату и участников; все UUID фиктивны.
2. `supabase/proposals/room-rpc-quotas-staging.sql`: применить **непубликуемое** SQL-предложение к тестовой базе.
3. `tests/fixtures/room-rpc-local-assertions.sql`: проверить закрытые права таблиц, отклонённые анонимные RPC, сохранение попыток ошибочного кода, третий отказ за окно, отсутствие доступа к чужому персонажу, успешное вступление и 10/10 бросков.
4. `tests/room-rpc-concurrency.mjs`: 16 параллельных обращений от одного фиктивного пользователя. Ожидаем 10 UUID и 6 отказов, без увеличения бюджетного счётчика выше лимита.
5. Продвижение в GitHub Pages теперь требует **успешного завершения и существующего полного build, и этого PostgreSQL job**. При ошибке SQL публикации не будет.

Это **испытание предлагаемого кода на реальном PostgreSQL** с синтетическим окружением; оно не является тестом Supabase Data API, настоящего OAuth и продуктивных RLS. Сами квоты в продуктивной Supabase **не установлены**.

## Восстановление DB + Storage — пока невозможно подтвердить

Проверено: текущий connector имеет функции SQL, но **не предоставляет** полный дамп базы, пользовательские JWT и содержимое приватного Storage через авторизованный канал. Инструмент сравнения `scripts/verify-restore.mjs` и восемь SHA-256 SQL таблиц готовы, но восстановленного проекта нет.

Для следующей проверки нужны:
1. Способ создать независимую среду, подтверждённая стоимость (или локальный Supabase CLI + Docker у оператора).
2. Конфиденциальный экспорт полноценной БД и **всех байтов** bucket `character-portraits`, выполненный на доверенной машине; не передавать в GitHub/чат.
3. Согласованный snapshot и тестовое восстановление DB, Storage и необходимых функций Supabase Auth. Сравнить содержимое таблиц и SHA-256 каждого объекта.
4. Два непривилегированных тестовых аккаунта с отдельными сессиями; запустить `scripts/security-two-accounts-e2e.mjs` из доверенного окружения, токены не публиковать.
5. Применить `room-rpc-quotas-staging.sql` **только в изолированном восстановлении**, проверить вызовы через Supabase REST API, права, регрессию UI и гонки.
6. И только потом выносить в `supabase/migrations` после ревью и подтверждённого rollback-plan.

**Опасные операции с продуктивной базой запрещены до подтверждённого восстановления.**
