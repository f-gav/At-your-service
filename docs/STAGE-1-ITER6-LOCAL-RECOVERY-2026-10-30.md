# Этап 1 · Итерация №6 — локальное восстановление в Docker (30.10.2026)

**Статус:** инструменты подготовлены; реальное восстановление пользовательского DB+Storage бэкапа ещё НЕ выполнено. Продуктивная Supabase не изменялась.

## Цель и ограничения

Воспроизводимый бесплатный путь для Windows 11: Supabase CLI + Docker Desktop + Node.js 22+ + PostgreSQL 17 CLI (`psql` и `pg_dump`). Рабочий проект: `cvimyqmksxeigjnofexf` (**At your service!**). Второй проект WreckTrack не трогать.

Обязательное различие:
- **Supabase CLI `db dump`** выгружает приложение/роли/данные, но исключает управляемые схемы `auth` и `storage`.
- `pg_dump --data-only --schema=auth` дополнительно сохраняет Auth-данные (очень чувствительные). Не переносить действующие Auth-сессии в доступную извне среду.
- **Байты `character-portraits` выгружаются отдельно** через Storage API/CLI. `storage.objects` не является файловой копией.
- Три независимых запуска дампа и Storage могут отражать разные моменты. Скрипт сравнивает два агрегированных снимка до/после и требует отсутствие изменений, но это **не строгая атомарная snapshot-гарантия**. Для сертифицированного согласованного комплекта нужен короткий операторский режим без записей и контроль полного восстановления.
- Восстановление только в совершенно новом локальном Docker-проекте, не в базе сайта и не в WreckTrack.
- Скрипт локального E2E использует два **вымышленных** аккаунта Supabase Auth. Настоящий Google OAuth отдельно проверяется ручной приёмкой и не помечается как прошедший.

## 1. Подготовить рабочее окружение на Windows 11

Установить и проверить:
- Docker Desktop (Linux containers; engine запущен)
- Node.js 22+
- Supabase CLI через официальный Scoop/Homebrew способ или как закреплённую версию локального инструмента
- PostgreSQL 17 клиент (`psql` и `pg_dump` в `PATH`)

Проверять актуальные флаги: `supabase --help`, `supabase db dump --help`, `supabase storage cp --help` и `supabase status --help`.

Подготовить **пустую закрытую папку вне Git** (пример `C:\\AYS-Private-Recovery\\snapshot-001`). Не использовать облачную синхронизацию, публичную папку или директорию исходников.

В PowerShell открыть корень репозитория:
```powershell
$env:AYS_RECOVERY_ROOT = 'C:\AYS-Private-Recovery\snapshot-001'
$env:AYS_SOURCE_PROJECT_REF = 'cvimyqmksxeigjnofexf'
node scripts/local-recovery.mjs preflight
```

**Никогда** не помещать пароли, JWT, SQL-дампы или приватные портреты в GitHub, Actions, чат, коммит и `VITE_*` браузерные переменные.

## 2. Только чтение: экспорт source DB и приватного Storage

Войдите локально в Supabase CLI и привяжите его к **конкретному проекту**, проверив адрес и ref:

```powershell
supabase login
supabase link --project-ref cvimyqmksxeigjnofexf
```

CLI попросит авторизацию/пароль в приватном окружении. Не используйте `supabase db push`, `db reset --linked` или `migration up --linked` — эти действия изменяют рабочую базу.

Для сбора read-only агрегатов через PostgreSQL нужна отдельная операторская сессия. На локальном Windows поставьте `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` **в окружение только локального PowerShell**. Имя хоста и пользователя берите из Supabase Dashboard → Connect; пароль вводите безопасно, не в Git или аргументы команды. Например:

```powershell
$env:PGHOST = '<database-host-from-Dashboard>'
$env:PGPORT = '5432'
$env:PGDATABASE = 'postgres'
$env:PGUSER = '<database-user-from-Dashboard>'
$env:PGPASSWORD = '<set-locally-only>'
node scripts/local-recovery.mjs backup
```

Рекомендуется отдельная короткая пауза редактирования пользователями на время бэкапа. Скрипт:
1. Проверяет точный project ref и запрещает перезаписывать существующую папку.
2. Делает `supabase db dump --linked` для `roles.sql`, `schema.sql`, `data.sql`; источник — только чтение.
3. Делает отдельный локальный `pg_dump --schema=auth --data-only`.
4. Выгружает все байты `ss:///character-portraits` через `supabase storage cp --linked --experimental -r`.
5. Сравнивает read-only контрольные суммы восьми таблиц и количество объектов до и после.
6. Сохраняет `source.json` и хеши дампов в приватном каталоге. Дамп не считается полноценной проверкой восстановления до следующего шага.

Если у текущей версии CLI отличается поведение копирования каталога Storage, скрипт завершится с ошибкой проверки количества файлов; вручную сверить пути относительно корня bucket. Не объявлять PASS при ошибке.

**Внимание:** пароль `PGPASSWORD` остаётся в текущем PowerShell-процессе; после завершения удалить из окружения: `Remove-Item Env:PGPASSWORD`. Не передавать его в аргументах CLI, где его могут видеть другие локальные процессы.

## 3. Восстановить только в Docker на том же компьютере

```powershell
node scripts/local-recovery.mjs restore
```

Создаётся новая папка `local-only`, `supabase init` и `supabase start`, без `supabase link`. Скрипт направляет `psql` **только** на `127.0.0.1:54322` (локальная Docker-БД с отдельным стандартным паролем), импортирует роли, схему, Auth-данные и данные приложения. Затем создаёт локальный приватный bucket, загружает файлы через `supabase storage cp --local`, выгружает их обратно и сравнивает:
- 11 счётчиков, 9 проверок целостности;
- SHA-256 содержимого строк 8 таблиц;
- число, пути и SHA-256 каждого объекта приватного Storage.

Если `psql` выявит конфликты версий Supabase/Auth, импорт останавливается с ошибкой без перезаписи production. Нужно разбирать совместимость локальной и hosted-версии схемы и аккуратно пересоздавать **только локальную** тестовую среду. Не править рабочую БД ради прохождения теста.

После успешной проверки **без изменения пользовательских записей** есть локальный файл `restored.json`. Только этот файл (и фактический успешный импорт) является допуском к E2E.

## 4. Реальные локальные JWT и RPC (не Google OAuth)

```powershell
node scripts/local-jwt-e2e.mjs
```

Сценарий читает JWT-ключи **только** из вывода локальной `supabase status -o env`, не записывая их на диск; создаёт два случайных непривилегированных Auth-аккаунта, две карточки персонажей и тестовую комнату в локальной БД. Загружает тестовый портрет, применяет подготовленную SQL-квоту **только к локальной БД**, затем запускает исходный `security-two-accounts-e2e.mjs`: проверяет реальные выданные Auth JWT, RLS, запрет чужого портрета, отсутствие доступа к чужой комнате/журналу и негативные RPC POST.

Ключи и пароли в ответ не печатаются. Нельзя выдавать тестовые JWT за пользовательские OAuth-токены. Этот шаг **может изменять только восстановленную локальную копию**, поэтому запускать его **после** успешной сверки с оригиналом.

Для отдельной проверки Google OAuth потребуются два реальных непривилегированных аккаунта в безопасной тестовой среде; не передавать действующие production JWT в чат.

## 5. Что учесть при аттестации восстановления

- Это локальный план полного восстановления **прикладной БД + Auth-данных + Storage-байтов**, но внешние секреты OAuth, настройки сервисов, SMTP, edge functions, JWT signing keys и системные настройки managed Supabase нужно отдельно реконфигурировать. Наличие SQL-дампа не доказывает восстановление всех компонентов платформы.
- `pg_dump` управляемой `auth` схемы может потребовать согласования версий локального Supabase и hosted 17.11. Не подавлять ошибки загрузки Auth.
- Восстановленный snapshot может содержать конфиденциальные реальные данные: отключить доступ к локальным портам из сети, зашифровать каталог хранения, не использовать его как публичный staging.
- Цепочка восстановления **не запускается в GitHub Actions на настоящих данных**: CI проверяет синтетические тесты и безопасность скриптов, а исходный архив обрабатывается только на доверенном компьютере.
- Подготовленные серверные RPC-квоты ещё не устанавливать в production до реального восстановления и отрицательных API-тестов.
