# Этап 1 · Итерация 3 — RPC комнат, реальные JWT, резервирование

Дата: 29 октября 2026 г. Статус: **частичная готовность**. Никакие серверные миграции и настройки продуктивной Supabase здесь не изменяются.

## 1. Что действительно проверено

- Код RPC `join_game_room` и `post_game_room_roll`: обе функции исполняются с `SECURITY DEFINER`, проверяют `auth.uid()`, принадлежность персонажа и системную совместимость. Для публикации броска требуется `casts_enabled=true`. SQL-привилегии запрещают анонимные вызовы и прямые `INSERT` в таблицы членства/журнала.
- Итерация 2: RLS PostgreSQL смоделирована для владельца, участника и постороннего в транзакциях `READ ONLY` с `SET LOCAL ROLE authenticated`. Изоляция чтения прошла. **Это НЕ настоящие OAuth JWT.**
- Новые тесты и проверки контрольных сумм выполняются только на синтетических локальных объектах и файловых данных. Рабочая БД не изменялась.

## 2. Реальные JWT: инструмент E2E

`scripts/security-two-accounts-e2e.mjs` работает с двумя **реальными непривилегированными** токенами Supabase Auth. Подготовить два отдельных пользовательских аккаунта, у обоих должен быть персонаж; первый владеет тестовой комнатой (с участником), второй НЕ состоит в ней. Нужен существующий портрет первого аккаунта. Инструмент проверяет `/auth/v1/user`, персональный доступ к `characters`, отсутствие чужих портретов, право владельца на комнату, невидимость комнаты/журнала постороннему, отсутствие `sheet_admins`.

Запускать только локально на доверенном компьютере, где можно безопасно задать переменные окружения (не вставлять токены в переписку, скриншоты, GitHub Actions или репозиторий):

- `AYS_E2E_SUPABASE_URL` — HTTPS API URL тестируемого Supabase-проекта.
- `AYS_E2E_PUBLISHABLE_KEY` — клиентский publishable key.
- `AYS_E2E_OWNER_JWT` — действующий пользовательский access token владельца тестовой комнаты.
- `AYS_E2E_OUTSIDER_JWT` — действующий access token постороннего.
- `AYS_E2E_ROOM_ID` — UUID существующей тестовой комнаты.
- `AYS_E2E_OWNER_PORTRAIT_PATH` — Storage-ключ портрета, который действительно принадлежит владельцу.

Команда запуска:

```bash
node scripts/security-two-accounts-e2e.mjs
```

По умолчанию **только чтение** и HTTP GET. Содержимое файлов Storage не загружается в память и не выводится в отчёт. Ни один JWT или идентификатор персонажа скрипт не печатает.

### Тесты RPC, потенциально изменяющие данные

Включать только после восстановления **отдельного** тестового Supabase-проекта:

- `AYS_E2E_ISOLATED_RESTORE=YES`
- `AYS_E2E_ALLOW_RPC_WRITES=YES`
- `AYS_E2E_PRODUCTION_PROJECT_REF` — ref продуктивной БД (скрипт откажется делать RPC, если URL ему соответствует).

Сценарий использует аккаунт постороннего: пытается вступить в комнату, выдавая чужой `character_id`, и отправить бросок чужим персонажем. Оба POST должны быть отвергнуты. Запросы по-настоящему **потенциально мутирующие**, поэтому на рабочем проекте скрипт не выполняет их даже при ошибке настройки. Для атаки с перебором кодов или нагрузочного теста этот инструмент НЕ предназначен.

Если реальных пользовательских JWT нет, проверка помечается **NOT RUN**, а не «успешно».

## 3. Полное резервирование PostgreSQL + приватного Storage

Официальная документация Supabase: https://supabase.com/docs/guides/platform/backups . Важно: DB backups хранят **метаданные Storage**, но **не байты изображений**.

Операторская последовательность:

1. Снять `supabase/backup-integrity.sql` и сохранить результат локально в защищённом каталоге; зафиксировать коммит и список миграций. Для согласованного снимка временно исключить изменения пользователей либо применить согласованную стратегию snapshots/моментов резервирования.
2. На доверенной машине с секретами доступа выполнить `supabase db dump --db-url "..."` по актуальной инструкции `supabase --help` / https://supabase.com/docs/reference/cli/supabase-db-dump . Для полного приложенческого бэкапа нужно сохранить схему и данные. Исключения managed-схем и ролей сверять с актуальной документацией, а не предполагать, что один дамп восстановит Auth.
3. Независимо выгрузить **все байты** private bucket `character-portraits` через защищённый Storage API/CLI или S3-клиент, сохраняя объектные пути и хеши. https://supabase.com/docs/guides/storage/management/download-objects
4. Хранить DB дамп, Storage, метаданные OAuth, ревизию и шифрованные секреты раздельно в защищённом хранилище. Не размещать архивы в GitHub или публичном CI.
5. Только после согласования расходов подготовить новый *изолированный* Supabase-проект. Проверить совпадение исходной и восстановленной схем, ролей, функциональности Auth, RLS, данных комнат и портретов. **Нельзя** восстанавливать поверх рабочего проекта.

### Детерминированная сверка результатов восстановления

`scripts/verify-restore.mjs` сравнивает два контрольных отчёта БД (источник и восстановление) и **SHA-256 каждого файла Storage** из двух приватных директорий. Он не скачивает файлы и не обращается к БД.

Формат `source.json` / `restored.json`: JSON-объект
```json
{
  "counts": {
    "characters": 0, "admins": 0, "published_templates": 0,
    "template_drafts": 0, "template_versions": 0,
    "portrait_objects": 0, "new_portrait_references": 0,
    "legacy_portrait_references": 0, "game_rooms": 0,
    "room_members": 0, "room_rolls": 0
  },
  "integrity": {
    "missing_source_objects": 0, "missing_card_objects": 0,
    "missing_sheet_objects": 0, "unreferenced_portrait_objects": 0,
    "versions_with_missing_template": 0, "invalid_room_memberships": 0,
    "broken_room_roll_links": 0, "malformed_member_snapshots": 0,
    "malformed_roll_dice": 0
  }
}
```
Заполнять **реальными числовыми агрегатами** из `backup-integrity.sql` в каждой среде; нули выше — только образец формата. Для обеих директорий сохранить пути относительно корня bucket. Команда:

```bash
node scripts/verify-restore.mjs source.json restored.json private-source/ private-restored/
```

PASS означает одинаковые количества строк, отсутствие девяти нарушений связей и точное совпадение путей, размеров и SHA-256 файлов Storage. Это **не полное доказательство** равенства содержимого каждой строки SQL и готовности всей инфраструктуры Auth: дополнительно проверить точечные контрольные JSON/PDF и тест двух JWT.

## 4. Ограничения частоты

В браузере введён быстрый *best-effort* предохранитель: не более 2 попыток вступления за 10 секунд и 10 трансляций бросков на персонажа за 10 секунд. Локальные броски кубиков никогда не теряются. Настройки сбрасываются после перезагрузки и могут быть обойдены прямым REST-запросом.

**Серверный rate limit ещё НЕ введён.** Не считать UX-защиту защитой от перебора кода. В будущей DB-итерации после проверенного восстановления:

1. Спроектировать серверный учёт неудачных попыток, в том числе неверных кодов, с сохранением учёта даже после ошибок RPC.
2. Рассмотреть Edge Function с ограничениями по пользователю и по IP плюс блокировку прямого обхода RPC либо изменение RPC на структурированный `{success,error}` без откатывающего счётчик исключения.
3. Ограничивать число событий бросков и размер payload; учесть конкурентные обращения и мониторинг блокировок.
4. На **изолированной** БД прогнать отрицательные тесты, конкурентные запросы и восстановление, затем миграцию на прод только с проверенным бэкапом и планом отката.

**Важно:** простой `INSERT` в таблицу счётчиков перед `RAISE EXCEPTION` внутри одной PostgreSQL RPC **не обеспечивает** rate limit: транзакция откатит счётчик вместе с ошибкой.

## 5. Незакрытые критерии этапа 1

- [ ] Наличие двух реальных непривилегированных пользовательских JWT и успешный read-only E2E.
- [ ] Подтверждённое восстановление согласованного DB+Storage snapshot в изолированной среде.
- [ ] Negative RPC POST в изолированной среде, в том числе конфликтные попытки.
- [ ] Серверный rate limit и проверенный план его развертывания.
- [ ] Ручной тест автосохранения одного листа с двух устройств.
- [ ] Правило «**один персонаж — одна комната**» сохраняется как утверждённое требование для будущего блока Rooms V2; сейчас не менять.

До выполнения пунктов этап 1 не отмечать завершённым.
