# At your service! — контрольная точка 0.2.4: безопасность

Дата аудита: 17 октября 2026. Проверка живой Supabase проводилась только SELECT-запросами метаданных; таблицы персонажей и содержимое приватного Storage не выгружались. Исходные политики сопоставлены с текущей базой.

## Подтверждено в действующей Supabase

- Все пять таблиц `public.characters`, `public.sheet_admins`, `public.sheet_templates`, `public.sheet_template_drafts`, `public.sheet_template_history` используют RLS.
- `characters`: четыре политики SELECT/INSERT/UPDATE/DELETE действуют для `authenticated` и сравнивают `auth.uid()` с `user_id`; для INSERT/UPDATE есть проверка нового владельца.
- `sheet_admins`: авторизованный пользователь может прочитать только собственное назначение; INSERT обычному `authenticated` не разрешён.
- `sheet_templates`: чтение для авторизованных пользователей; INSERT/UPDATE только при наличии подтверждённой записи в `sheet_admins`. Драфты и история доступны административной роли по RLS.
- `publish_sheet_template(text)`: `SECURITY INVOKER` (без `SECURITY DEFINER`), пустой `search_path`, серверная проверка наличия администратора и ключа шаблона. `reorder_characters(uuid[])` тоже `SECURITY INVOKER` и сверяет полный набор своих ID.
- Анонимная роль не имеет SELECT в `characters`, INSERT в `sheet_admins` и EXECUTE обеих RPC. Роль `authenticated` получает право вызова RPC и DML через права SQL, но окончательный доступ ограничен RLS и условиями функций.
- Storage bucket `character-portraits`: `public=false`, только `image/webp`, максимальный размер 450000 байт. Три политики SELECT/INSERT/DELETE требуют `auth.uid()`, принадлежность папки пользователю и существующего принадлежащего ему персонажа. Для загрузки имя должно соответствовать формату изображения.
- Конфигурация браузера использует только `VITE_SUPABASE_PUBLISHABLE_KEY`, а не сервисный секрет.

## Подтверждённое исправление 0.2.4

**Изоляция административного интерфейса при смене аккаунта.** Ранее флаг `isTemplateAdmin` сбрасывался при выходе, но до ответа сервера при переключении авторизованных аккаунтов мог временно отражать предыдущего пользователя. Теперь оба состояния `isTemplateAdmin` и `showTemplateAdmin` сбрасываются **сразу** при изменении ID пользователя, затем выполняется новая серверная проверка. Это устранение временного отображения админ-кнопок, не исправление обхода RLS.

## Автоматизация аудита

- `supabase/security-audit.sql` — только читающая сводка фактического состояния RLS, привилегий ролей, RPC, bucket и списка политик. Не возвращает ID пользователей, JSON персонажей и пути файлов.
- `tests/models.mjs` — запрещает изменяющие SQL-операторы в файле аудита, проверяет наличие ключевых блоков и немедленный сброс прав интерфейса.

## Замечания Supabase Advisor

- Security: **Leaked Password Protection Disabled** — проверить включение защиты от скомпрометированных паролей, если в Auth используется парольный вход. Приложение применяет Google OAuth. Руководство: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection
- Performance (не уязвимость): два индекса внешних ключей отсутствуют у `sheet_template_drafts.updated_by` и `sheet_template_history.published_by`. Пока не создавать индексы на рабочей БД без утверждённой миграции. Документация: https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys

## Что ещё необходимо до абсолютной приёмки

**Не выполнены настоящие межпользовательские E2E-тесты** с двумя непривилегированными аккаунтами A/B: попытки доступа к чужим персонажам, чужим Storage-путям и публикации шаблонов. Проверенные определения политики и текущие привилегии дают основание считать настройку защищённой, но не заменяют отдельную проверку с реальными JWT в изолированной тестовой среде.

Открыта контрольная точка **0.2.2**: резервная копия рабочей БД/Storage не восстановлена в тестовом проекте. Никаких миграций, изменений Auth, данных пользователей и игровых правил не выполнялось.

## Критерий выпуска

Запустить `npm run test:models`, сборку TypeScript/Vite, тесты PDF и браузерные PF2e/библиотеки и убедиться, что `build` и `deploy` успешны для одного и того же финального SHA.
