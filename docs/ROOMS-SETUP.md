# Комнаты At your service! — первый релиз (PF2e и Project Moon)

Основано на концепции Vortex/Long Story Short, но работает **только в собственной базе At your service!**.

## Готовые возможности

- Мастер входит через Google и создаёт именованную комнату, выбирая систему
  **Pathfinder 2e** или **Project Moon**. Смена системы существующей комнаты
  запрещена. Код приглашения — 8 случайных символов в верхнем регистре.
- Игрок входит под своей учётной записью, вводит код и выбирает собственного
  персонажа. Серверная функция `join_game_room` проверяет владельца, систему,
  существующее участие и лимит участников. Несовместимый персонаж **не
  подключится даже через прямой REST-запрос**. Сейчас один персонаж может
  состоять только в одной комнате.
- Мастер видит участников и может исключить персонажа, закрыть/открыть
  приглашения или удалить комнату. Игрок может покинуть комнату сам.
- Pathfinder показывает текущие/максимальные ПЗ, временные ПЗ, КД и уровень.
  Project Moon показывает текущие/максимальные HP, ST, SP и ранг.
  В Project Moon максимумы поддерживают существующий `autoVitals`.
- Автосохранение листа обновляет маленькую безопасную сводку по базе.
  Подписка Supabase Realtime обновляет карточки и журнал, есть опрос
  раз в 8 секунд на случай обрыва соединения.
- Общий журнал бросков: существующий `DiceRollPanel` отправляет событие
  из подключённого листа с формулой, гранью, расчётом и результатом.
  Галочка «Отправлять броски в комнату» временно отключает отправку.
  История последних 80 бросков отображается в комнате; записи сохраняются в базе.
- Другие игроки и мастер **не получают полную запись** `characters.details`,
  портреты из приватного Storage или приватные заметки.
  Только владелец может открывать свой лист. Сведения комнаты лежат в
  `game_room_members.snapshot`, содержащем исключительно ресурсы.

## Обязательное включение Supabase

**Важно:** в подключённых к этой сессии Supabase-аккаунтах найден проект
`WreckLib`, но **не** Supabase-проект At your service!. НЕЛЬЗЯ применять
SQL комнат к WreckLib: он связан с другим сайтом.

Чтобы реально активировать комнаты:
1. Откройте **Supabase-проект, URL которого используется в GitHub Actions
   для At your service! в `VITE_SUPABASE_URL`**.
2. Сделайте резервную копию данных/схемы, затем откройте SQL Editor этого
   Supabase-проекта и примените **ровно один раз**
   `supabase/migrations/20261026_game_rooms.sql`.
   Существующая таблица `public.characters` и её RLS сохраняются.
3. Убедитесь, что в SQL Editor имеются три таблицы:
   `game_rooms`, `game_room_members`, `game_room_rolls`, обе функции RPC
   `join_game_room` и `post_game_room_roll`, а RLS включён на всех
   трёх таблицах. Для обновлений Realtime должна быть включена публикация
   `supabase_realtime` этих таблиц (делает сама миграция).
4. Войдите с двух реальных Google-аккаунтов и проверьте:
   - Мастер создаёт PF2e комнату; PF2e игрок входит по коду.
   - Персонаж Pr. Moon отвергается этим же кодом **с сервера**.
   - При изменении ПЗ/КД и сохранении листа обновляется карточка мастера.
   - Бросок со включённой отправкой появляется у мастера; отключённый —
     остаётся только локально.
   - Другой пользователь не может открыть `characters.details` участника
     и изменить ресурсы чужой карточки напрямую.
   - В новой комнате Project Moon синхронизируются HP, ST и SP.
   - Удаление комнаты не удаляет персонажей и их данные.
5. Запустите `supabase db advisors` или Security Advisor проекта и
   отдельно пройдите межаккаунтные RLS-проверки.

При отсутствии миграции вкладка комнат выводит объясняющую ошибку;
основные листы персонажей продолжают работать как прежде.

## Архитектура и ограничения

Схема:
`game_rooms` — мастер, система, название, уникальный код, статус;
`game_room_members` — персонаж, владелец, видимость бросков,
компактная автоматически обновляемая сводка;
`game_room_rolls` — безопасно ограниченное тело броска.
Весь доступ через Google/Supabase Auth и RLS. Внешнего Vortex API нет.

В первой версии мастер видит **только ресурсы, а не полный лист**,
не может напрямую менять чужие ПЗ и КД, нет чата, инициативы или
интеграции Discord/Telegram. Броски рассчитываются на устройстве
игрока, поэтому журнал **не является криптографически проверяемым**;
для соревновательной игры позже нужен серверный RNG.
Удаление комнаты уничтожает только её членство и журнал.
Код комнаты надо передавать только приглашённым игрокам.
Лимит одной комнаты — 24 персонажа; для предотвращения злоупотребления
кодами понадобятся серверные rate limits на следующем этапе.

Следующий этап: мастерские действия лечения/урона, возможность скрывать
точные значения ПЗ, события состояний/заклинаний, фильтры и журнал
с большим сроком хранения, server-authoritative броски, дополнительные
средства управления ролями и внешние интеграции.
